# Zesislar

Verify the Zesu SSZ decoder binary in Coq using Islaris, against the Sail RISC-V ISA semantics.

The target is the same `zesuSszDecodeRv64Elf` binary verified in
[binary-fv-experiment](https://github.com/codygunton/binary-fv-experiment) via the Lean route.
This repository explores the alternative: let Isla handle the ISA semantics, and use Lithium's
proof search to automate what the Lean route does by hand.

## Context

`binary-fv-experiment` proves compliance of the Zesu SSZ decoder against a Sail-extracted EVM
specification. It works directly against the Sail-to-Lean extraction of the RISC-V model — roughly
16k lines of Lean carry the ISA semantics through the proof. Every feature gate, every alignment
check, every address-translation branch is a proof obligation.

Islaris replaces that with a trust trade: Isla symbolically executes the Sail model outside Coq,
prunes infeasible paths via z3, and emits per-instruction traces as Coq terms. The proof search
walks those traces. The ISA semantics are trusted, not proved.

See [islaris-tutorial](https://github.com/codygunton/islaris-tutorial) for the technique on small
examples.

## What this repository will show

1. Whether islaris scales to the Zesu binary (~100k+ instructions).
2. What the dump annotation burden looks like at that scale.
3. Whether the proof search can handle the Zesu contract structure, or whether the residual goals
   are prohibitive.
4. How the trust boundary compares to the Lean route.

## Guidance from the islaris-tutorial experience

### The machine description

Start with `islaris-tutorial/IslarisTutorial/riscv64_tutorial.toml` and adjust. The Zesu binary
runs in Machine mode with no address translation. Pin:

- `misa.bits` concretely (enables M extension, disables C — the binary is rv64im)
- `cur_privilege = "Machine"`
- `mstatus.MPRV = 0` via `[constraints] reset`

These eliminate thousands of feature-gate and privilege-check branches globally.

### The dump annotation strategy

The dump is the bottleneck at scale. Three kinds of annotation:

1. **`//@isla-config:`** — one line, once, at the top. Points to the toml.
2. **`//@constraint:`** — per-instruction, for operand-dependent facts (pointer alignment, RAM
   bounds). At 100k instructions, most will need none. Loads and stores need alignment and
   address-range constraints.
3. **`//@spec:` + `//@import:`** — the scaling mechanism. Without these, every instruction is
   stepped from its trace. With them, common instructions (mv, add, ld, sd, li, etc.) are proved
   once in `InstrSpecs/` and reused. **Build the instruction-spec library early.** The RV64IM
   instruction set has ~50 distinct opcodes; a library of specs for the 20 most common covers
   the vast majority of the binary.

### What will be hard

**Loops.** Every back edge needs an invariant. The Zesu binary has many loops. Each invariant must
be written by hand. If a loop carries a ghost variable (one not visible in any register), the proof
needs `liInst` to instantiate it — the search cannot guess it.

**Observable traces.** If the specification talks about memory writes (as the SSZ decoder does),
the invariant must track the remaining trace. A `Fixpoint` on `nat` does not reduce over symbolic
values; manual `destruct` is needed before each store. This is a known friction point.

**Residual arithmetic.** Every `bltu`/`bgeu` produces a shelved goal requiring a bridge lemma
(`bv_zero_extend_128_lt`). Every `ld` produces a `bv_sign_extend_64_unsigned` goal. These are
one-time lemmas but must be registered. A `can_solve_hook` override could close many of them
inline.

**Scale.** Isla generates one trace file per instruction. At 100k instructions, trace generation
takes hours. `make traces` is embarrassingly parallel (`-j` flag), but the generated directory will
be large. Consider splitting the binary into function-level chunks and verifying them independently.

### What should be easy

**Straight-line code.** `repeat liAStep; liShow.` handles it. No invariant, no manual steps.

**The machine description.** One toml file, shared across the entire binary. The islaris-tutorial's
config is a starting point; adjust `misa.bits` for the exact extensions Zesu uses.

**Reusable instruction specs.** `mv_spec`, `add_spec`, `ld_spec`, `sd_spec` etc. cover most of the
instruction mix. Write them once in `InstrSpecs/`, register with `LithiumUnfold`, and the dump
annotations invoke them.

### Trust boundary comparison

| | Lean route | Islaris route |
|---|---|---|
| ISA semantics | proved (16k lines) | trusted (Isla) |
| Feature gates | proved per instruction | pruned by z3, trusted |
| Alignment checks | proved per load/store | pruned or residual |
| Specification | Lean function | Coq definition |
| Proof automation | custom tactics | Lithium search |
| Per-instruction cost | high (full model) | low (trace walk) |
| Trust base | Lean kernel | Lean kernel + Isla + z3 |
